## Immediate source block

Choose the active firewall manager. Existing `renvix_origin` nftables users should add the element directly; the static initializer now also includes it for a fresh installation:

```bash
sudo nft add element inet renvix_origin banned4 '{ 45.115.26.203 }'
sudo nft list set inet renvix_origin banned4
# Persist the updated table snapshot through the existing refresh controller;
# supply ALL actual public ingress interfaces, never assume eth0.
sudo env PUBLIC_INTERFACES=ACTUAL_PUBLIC_NIC /usr/local/sbin/origin-lockdown.py
```

On a host using iptables instead:

```bash
sudo iptables -w -C INPUT -s 45.115.26.203 -j DROP 2>/dev/null || sudo iptables -w -I INPUT 1 -s 45.115.26.203 -j DROP
# On a host managed by iptables-persistent, save this static rule BEFORE Fail2ban starts:
sudo netfilter-persistent save
# If Docker publishes the protected port, also place a DROP before its FORWARD accept:
sudo iptables -w -C DOCKER-USER -s 45.115.26.203 -j DROP 2>/dev/null || sudo iptables -w -I DOCKER-USER 1 -s 45.115.26.203 -j DROP
```

Do not run the Docker command if the host does not use Docker's iptables backend. Reapply that DOCKER-USER rule after Docker starts via its firewall manager; do not save Docker's transient chains with iptables-persistent. The origin firewall sees Cloudflare proxy source IPs on proxied requests, so this kernel rule blocks **direct-to-origin** traffic only. The account-edge rule below blocks the visitor through Cloudflare.

For account-wide Cloudflare Block, configure `CF_ACCOUNT_ID` and `CF_EDGE_BLOCK_TOKEN` in `/etc/renvix-secops/edge.env` (0600) and run:

```bash

sudo /usr/local/sbin/edge-escalate ip 45.115.26.203
```

## Edge path rule

Use the exact expression in `cloudflare-probe-expression.txt` as a **zone-level WAF custom rule** with action `block`. It excludes `admin.renvix.app`, the isolated honeypot, so its Worker can observe two hits and ban the visitor. Install it with `sudo install -m 0750 deploy/security/install-probe-waf /usr/local/sbin/install-probe-waf` and `sudo /usr/local/sbin/install-probe-waf deploy/security/cloudflare-probe-expression.txt`, or use the Cloudflare dashboard. The script updates only its own rule in the `http_request_firewall_custom` entrypoint and preserves other rules. It requires `CF_API_TOKEN` and `CF_ZONE_ID` in `/etc/renvix-secops/cloudflare.env` (0600), with Zone WAF Write permission. If the honeypot host is changed, update the exception first. Cloudflare WAF can return an HTTP block only after TLS negotiation; it cannot suppress the edge TLS handshake.

The expression uses case-normalized paths and covers `/.env*`, `/.git*`, `/actuator`, `/wp-admin` and `/wordpress`. Verify that those paths are unused by legitimate applications. Nginx returns 444 for those decoys and PHP/ASP/JSP probes before any upstream proxy pass. Keep the decoy access log enabled: disabling it makes Fail2ban ineffective.

## Host automation

Install `ipset`, `iptables`, `ip6tables`, Fail2ban, Python 3 and Nginx. Install these repository files into the matching paths:

```bash
sudo install -m 0750 deploy/security/ipset-probe-action /usr/local/sbin/ipset-probe-action
sudo install -m 0750 deploy/security/sync-cloudflare-realip.py /usr/local/sbin/sync-cloudflare-realip.py

sudo install -m 0750 deploy/security/probe-incident /usr/local/sbin/probe-incident
sudo install -m 0644 deploy/security/probe-log.conf /etc/nginx/conf.d/00-probe-log.conf
sudo install -m 0644 deploy/fail2ban/filter.d/honeypot-probes.conf /etc/fail2ban/filter.d/
sudo install -m 0644 deploy/fail2ban/action.d/honeypot-ipset.conf deploy/fail2ban/action.d/probe-json.conf deploy/fail2ban/action.d/probe-edge-access.conf /etc/fail2ban/action.d/

sudo /usr/local/sbin/sync-cloudflare-realip.py
sudo nginx -t
sudo fail2ban-client -t
sudo systemctl daemon-reload
sudo systemctl enable --now renvix-realip-refresh.timer
sudo systemctl restart fail2ban
```

Merge the `deploy/nginx.conf` server-level rewrite gate and dedicated `access_log` into **every** public TLS/HTTP server without overwriting its existing certificates or upstreams. `probe-log.conf` and the generated real-IP file belong in `http {}`. Verify that a proxied request logs the actual visitor IP and that forged `CF-Connecting-IP` on a direct request is ignored. Restrict origin 80/443 to Cloudflare IP ranges with `origin-lockdown.py`, including IPv6. Docker-published workloads need an equivalent pre-DNAT/FORWARD guard. For the `honeypot-scanner` action, the ipset INPUT rule affects host-local Nginx; for Docker Nginx move the set match into DOCKER-USER or an equivalent nftables forward hook after checking the host's firewall backend. The **Cloudflare action** protects proxied visitor traffic.

Set Fail2ban `[Definition] dbpurgeage = 691200` in `/etc/fail2ban/fail2ban.local` so its SQLite database retains all seven-day bans across reboot. Keep Fail2ban enabled on boot. `ipset` elements expire in kernel after seven days; the jail also unbans after seven days and its account Access Rule action deletes its dynamic rule. Monitor action failures: API outages can delay edge synchronization or expiry.

The separate Cloudflare Worker logs do **not** appear in `/var/log/nginx/honeypot-probes.log`. Its own Durable Object now counts two external page requests within 60 seconds, blocks via account IP Access Rule and schedules verified deletion after seven days. Set `EDGE_AUTO_BLOCK=true`, account ID, scoped token and Durable Object binding only after staging tests. This is the authoritative Cloudflare honeypot path; the host jail covers Nginx-origin decoys.

## Alert hygiene and checks

Apply database migration `0098_security_honeypot_digest.sql` **before** deploying the new cron code. It suppresses queued historical decoy-only emails. Future decoy incidents stay in the ledger and are grouped into a daily in-app notification; the existing daily `security-inspector` cron sends one digest per day/recipient, with idempotency and retries. Production-origin incidents retain immediate alert queueing. The 200-requests/second threshold needs an edge analytics stream or another global per-second counter with its own alert subscription; it is **not implemented or activated** here. Cloudflare's WAF rate-limiting `period` values begin at 10 seconds on supported plans, so a 2,000-per-10-second rule is only an average approximation, not an exact 200-RPS detector. Do not claim global RPS from the honeypot's per-request DB writes.

```bash

# Roll back the controlled test source:
sudo fail2ban-client set honeypot-scanner unbanip TEST_SOURCE_IP
```

Do not fire test decoy requests from an operator's shared/NAT production IP. At Cloudflare, verify one request reaches the Worker, the second creates an account rule, later requests are blocked, and the seven-day alarm deletes only the matching Worker-owned rule. Normal application routes must remain 200. Through Cloudflare a Nginx 444 may appear as a proxy error instead of curl exit 52.
